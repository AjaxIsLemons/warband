## Server question → the content version stamp

Jake: *"do we have a server set up? I assume we will want some kind of cloud storage especially if we
end up adding PvP aspects back yeah?"* → then *"not something that needs to be built today. let do
it"* on the one prerequisite.

**Answer.** No server, and zero networking in the codebase. But homeserv already runs Caddy, Docker,
Tailscale split-DNS and a native Palworld server, and Shoota has a Unity LinuxServer build — so
hosting is a solved problem and deferring costs nothing. The clarification that matters: **every PvP
idea in the vault is asynchronous** (Echo exhibitions vs a stored snapshot, leaderboards, ghosts).
That is "upload a blob, download a blob" — a key-value store behind Caddy, not netcode. Real-time PvP
would be a different game, and nothing in ADR 0016 asks for it.

**The real gap, built.** ADR 0008 has specified `contentVersion` since 2026-07-22 and it never
existed — `Replay.cs` had a format version only. Now `IRunContent.ContentVersion`, a **computed**
FNV-1a-64 fingerprint of the whole content graph, not a hand-bumped constant (the failure mode is a
retune, which is exactly what a human forgets to bump). Stamped into `RunState` and `GhostSnapshot`,
checked on resume.

**Why the id check wasn't enough** — worth remembering, because it looks redundant: `Resume` already
resolves every id, so a *rename* fails loudly. But encounters derive from the seed at FIGHT time, so
identical ids with different numbers resume happily and then fight a different army than the save was
made against. No symptom. The hasher therefore walks the whole graph — selectors, conditions, fields,
pulses, mastery riders, patches — and a test proves a retune is caught at 11 different depths. A
shallow hash would have been worse than none: a guarantee it doesn't keep.

**Deliberately not done:** replays are not stamped. They store the full event log, so playback is
content-independent; bumping the format to v6 would force regenerating 10 fixtures for a reason that
does not hold. Re-simulation is what content changes break — saves and snapshots, which are stamped.

**Verification:** 433 tests. The algorithm is pinned to an independently-computed digest so nobody can
"simplify" it to `string.GetHashCode()` (per-process randomized → saves fail after restart, looking
exactly like corruption). Cross-machine: `Warband.Content.dll` is byte-identical on homeserv and
Windows. **Left undone:** the on-Windows harness run — `RunSaveCheck` was extended and synced, then
**Codex took the Unity lock** mid-verification. Not retried in a loop (per the lock protocol). Run
menu `Warband/Verify Run Save` when it frees; homeserv-side fingerprint for comparison is
`f1f4a7e9b5cd527b`.

## Item 8 — first standalone build, launcher, delivery (piggybacked on Shoota)

Jake: *"get to work on it. look at what we did for shoota too, it would be great for play testing if
we built a launcher and content delivery system, we can piggy back off that infra if needed."*

Read Shoota's pipeline first and copied its shape rather than inventing one: `deploy/ship-release.sh`
(pull → verify → zip → atomic publish), `launcher/main.go` (manifest → download → SHA-256 → atomic
install → launch), the `app.json`/Makefile target conventions. warband has no server, so the server
half is simply absent.

**The landmine was real — and the preflight caught it before a build was spent on it.** New
`Warband/Build Preflight` reported all six hand-HLSL shaders as "would be STRIPPED from a player
build". `GraphicsSettings.asset` held seven always-included shaders, every one a Unity built-in. All
six warband shaders are reached only through `Shader.Find` and referenced by no material asset, so
the first friend build would have silently lost the entire combat-spectacle arc — and it would have
looked like broken FX code, not a build setting. `WarbandBuild` now registers them itself on every
build and logs what it added; verified afterwards in `GraphicsSettings.asset` by mapping guid → meta.

**Built:** v0.1.260726.1352 · 162 MB · 0 errors · content `f1f4a7e9b5cd527b`. Publish produced a
58 MB zip + launcher manifest. Launcher verified end to end against a local HTTP server (cold
install, hash verify, atomic install with rollback, version marker, the stand-in exe genuinely ran,
second run short-circuits to "Up to date"), cross-compiles to a 6.1 MB Windows PE32+ binary.

**Two design changes vs Shoota's launcher, both deliberate:** the token is **optional** (Shoota's Go
site checks the header and hard-fails without it; warband serves a static manifest, so the gate can
be added later without reissuing launchers) and the zip URL is **resolved relative to the manifest
URL**, which means a plain static Caddy directory is sufficient — no application server at all.

**Closed an open question:** the content fingerprint computed inside Unity on Windows is
`f1f4a7e9b5cd527b`, identical to homeserv's. That was left unverified when the version stamp landed.

**Gotcha that cost a detour — worth remembering.** The built player appeared to create a `run.save`
on a cold boot, which would have meant the autosave hook was firing when no run existed. It is not:
deleting the save and relaunching produced none. The cause is that **the Editor and the built player
share `Application.persistentDataPath`** — the same directory holds `run.save` and the Editor's own
`Unity/…/Editor/Analytics`, so a Play Mode session (Codex was doing station verification earlier)
writes the file a friend build would read. Benign, but it is exactly why a fresh build can look like
it "already has a run".

**Not verified:** whether the built player boots to the menu and renders. Batchmode launches over SSH
produced no player log and no visible process, and a session cannot screenshot a player window. One
double-click by Jake settles it. Two sudo steps and the gate decision are also his —
`deploy/README.md` §"STILL NEEDS JAKE".

### Access decided: Discord sign-in gates the launcher, nothing else

Jake: *"no gate needed since this doesn't really need a server. I think if someone signs in with
discord, they can dl the launcher."*

Built `site/` — one Go file, Shoota's session/OAuth scheme (HMAC-signed cookie, state-cookie CSRF,
`identify` scope only) with the database, accounts, telemetry and admin cut out. `/launcher` requires
a session; **`/releases/*` is open on purpose.** That layering is the whole design: gating the release
files would mean embedding a secret in every launcher binary to un-gate them, and anyone can read it
straight back out of the exe. Shoota reached the same conclusion the hard way — its launcher README
notes the update zip is deliberately no longer tied to a browser Discord session. Gating the exe
download is honest about what it buys: friend-scale friction, not DRM. No allowlist, by design.

**Verified the gate both ways:** signed out, `/` offers sign-in and `/launcher` 302s to Discord while
`/releases/*` serves 200; signed in (forged-but-valid cookie, since the test secret was mine),
`/launcher` returns the exe byte-identical to the published one. Tampered and expired cookies are
both rejected.

**Then the real end-to-end:** the actual launcher pulled the actual 58 MB published build through the
actual site, verified SHA-256, installed 157 MB, and failed only at `exec` — a Windows PE on Linux,
which is the correct failure and proves every step before it. Also confirmed the shaders are not
merely *registered* but **physically present in the shipped `Warband_Data`**, with StreamingAssets
(tuning.json, tuning.ranges.json, 10 replay fixtures) alongside.

## First standalone play pass — two player-only shader landmines + audio muted

Jake's first real player pass booted through the menu and reached combat, closing the old
"does the exe run?" question but invalidating the visual review: the board floor, HP bars, and Mana
bars were pink. This was genuinely player-only. The player log provided hard proof for the first
landmine: the legacy Burst/Tracer path resolved `Universal Render Pipeline/Unlit` by name, received

`WarbandBuild` now treats URP Lit/Unlit as runtime shaders beside the six Warband shaders. The
preflight first failed exactly those two rows, the build registered them through Unity's serialized
Graphics Settings, and the post-build preflight passed. But Jake's direct rerun of

registered `Universal Render Pipeline/Lit` shader. Build `0.1.260726.1706` succeeded at 162.8 MB

## Combat opening — "every unit teleports somewhere" (render-only fix)

Jake, on the corrected standalone build: *"the start of combat is really jarring — once you press
start it seems like every unit teleports somewhere; we need normal traversal."*

Traced from the sim outward rather than from the pixels. The sim was innocent: it emits proper
`MoveStart`/`Move` pairs with real step windows (ADR 0018), and a headless probe of the fold showed
every walk interpolating correctly. What it also showed was **two units per affected fight changing
position on tick 0 with no `MoveStart` at all** — the authored `Leap`: Ambush (Shade passive) and
the Diver role (Gloamstalker, `AtStart(Leap(Farthest))`, "it is in your backline on tick 0").
Across 99 run fights: **24% open with 1–2 instant leaps, averaging 5.1 hexes** (max 6) on a board
whose corner-to-corner is 9.

Asked Jake before changing behavior; he chose the render-only fix over deleting the mechanic. Three
defects, all in `ReplayPlayer`/`tuning.json`, none in the sim:

1. **Flat air-time.** `DriveArc` already scaled arc HEIGHT with the jump ("a hop to the next hex
   should not launch like a cross-board dive") but its DURATION was a flat `motionSeconds` — 0.34 s
   whether it crossed one hex or five. New `TellDef.motionPerHexSeconds` + `motionMaxSeconds`:
   `motionSeconds` buys the first hex, each further hex adds 0.1 s, capped at 1.0 s. A 5-hex dive is
   now 0.74 s. Span is measured through the board's own projection, so retuning `hexSize` can't
   desync it.
2. **No opening beat.** It fired on the literal first frame of playback. New tuning-owned
   `playback.openingHoldSeconds` (0.7 s). The subtlety is the fold: arming folds to tick **−1**, not
   0 — folding to 0 would land the leapers before the hold elapsed, so the "held" board would be
   showing the fight's second frame.
3. **A pop hiding inside the pop.** Between dispatch and the tell's beat-stagger + windup, the body
   rendered on its LANDING hex, then snapped back to take off and flew. Found by frame-stepping in
   play mode, not by reading. Fixed by seating `MotionOffset` at the take-off on dispatch — exactly
   `DriveArc`'s own m=0 value, so the handoff is continuous.

**Verification.** Headless client compile (glob csproj vs Shoota's Unity reference assemblies,
negative-controlled on `ReplayPlayer.cs`); 433 sim/run tests green (sim untouched). In the editor,
A/B on the `wallfort` fixture — whose Shade already makes a ~5-hex tick-0 Ambush — at 0.45 s:
**before** = grounded on the landing hex mid-stab; **after** = airborne at y=2.39, mid-board. In
play mode, frame-stepped the gate: held on the take-off hex, released on schedule, no landing-hex
pop, playhead advances monotonically after.

**Note for whoever picks this up:** `wallfort`/`statusstorm` already carry long tick-0 Ambush leaps,
so the existing fixture set covers this — no new scenario needed.

## Pathing + targeting deep dive — units were idling entire fights (ADR 0025)

Jake: *"we have a major bug with our unit pathing. Units will just sit behind others in line... I
think I've seen the jump units jump, get stuck between two enemy units doing nothing because they
are 'targeting' another unit. Can you do a deep dive on the targeting and pathing, research how
other similar games do it and build a better system?"*

Reproduced both headlessly before touching anything, and both were worse than the report.

- **Blocked behind allies:** four bodies in a clump vs one enemy — the flank body logged **0 swings
  across the whole 1200-tick fight**.
- **The diver:** a `LowestHp` leaper into a full backline recorded **0 movements for the entire
  fight** and 13 swings (all after the storm had killed things loose). It stood still for ~1000
  ticks while five enemies ate it.

**Three independent causes, none of them the renderer.**
1. Movement was a **greedy hill-climb**: step only to a strictly-closer *free* neighbour. That is a
   local-minimum machine on a 6-wide board — one ally in the closing direction and the unit is done
   for the fight. Not a "sometimes suboptimal path"; a permanent freeze.
2. Targeting was **reachability-blind with no fallback**. Attacks only ever go to `TargetId`, so a
   unit whose pick is unreachable has *no behaviour at all* — it can't step and won't swing at the
   enemy standing next to it.
3. `LeapTo` **cleared `TargetId`** to "re-acquire nearest from the new position" — a comment older
   than `TargetPref`. For a `Farthest` diver, the farthest enemy *from your backline* is your front
   line, so the Gloamstalker dived and then walked back over the rank it had just jumped.

**Built** (`sim/Warband.Sim/Pathing.cs`, ~130 lines + the decide-phase rewrite): Dijkstra flow field
out from the **engage ring** — every hex the unit could actually *attack from*, clear projectile line
included, so closing / rounding a crowd / hunting a firing angle stopped being three special cases
and became one. Walls impassable; **a body is a detour, not a wall** (`BodyCost = 6`), which keeps a
gradient through a crowd and *is* the unit's patience for a queue. Then the **engagement law** —
can't reach it, can't hit it, fight what you can (Taunt exempt; heal-autos get the ally version) —
and a leap keeps the victim its selector chose.

**The subtle one, worth remembering.** First build still left the flank body stranded. Cause: goal
hexes were seeded at 0 regardless of occupancy — but a melee engage ring *is* the target's own
neighbourhood, which is exactly where your allies already stand. Seeding those at 0 tells everyone
queueing behind them that they have already arrived, so the whole team stops one hex short of a
target with free slots on its far side. Goals are now seeded at their own occupancy toll. The step
gate is likewise `<=`, not `<`: strictly-cheaper refuses the last step into a ring (a ring hex and
the route through it cost the same), and anything looser makes units orbit a full scrum forever.

**Gates.** 440 tests (new `PathingTests.cs`: routes round allies, routes round a wall, settles
instead of orbiting, boxed-in unit fights, taunt survives the fallback, diver keeps its victim,
determinism on a 10-body crowd). Golden replay + all 10 scenarios regenerated and round-tripping.
DLLs rebuilt into `Plugins/`. Baseline captured from a HEAD worktree so every number below is a real
A/B, not a memory.

**Two tests changed on purpose, both encoding old limitations as if they were laws.**
`PocketedShooterStandsInsteadOfOscillating` asserted *zero* moves — the one-hex angle seek could only
see its own six neighbours, so it gave up and lost to the storm; routing now walks it out of the
pocket and it kills the target by **tick 42**. And `AcquiredWith` put a rooted, reachable enemy
adjacent to the hunter, so the engagement law (correctly) diverted it — the hunter now has no reach
at all, which is what "test acquisition in isolation" actually needs.

**Measured on shipping content, not just the repros.** 264 real encounter fights (every node
encounter × 3 acts × 4 formations × 6 seeds; 2040 units), A/B'd against a HEAD worktree:

| | before | after |
|---|---|---|
| units that **never swing once** | 96 (4.71%) | **18 (0.88%)** |
| units frozen ≥3s (no move/swing/cast) | 390 (19.1%) | **198 (9.7%)** |
| dead time / living unit-ticks | 5.23% | **2.82%** |
| mean time to first swing | 14t | **10t** |

One unit in twenty used to spend a whole authored fight without swinging. Now it is one in a
hundred. (The audit instrument was temporary and has been deleted — recipe is in ADR 0025 if it
is ever worth re-running.)

**Consequence Jake needs to see: the encounters got harder because the enemy AI now works.**
`The Drop — AMBUSH` went **FREE — "every formation wins, it poses nothing yet"** → **POSES A PROBLEM,
100-point placement swing** (turtle 100%, back-line 0%). Its authored premise is literally "your
backline is the front line" — it never happened before because the ambusher walked home. The naive
line still completes 3/12 but now dies in **act 1** rather than act 2; bosses still admit 3-4 answer
axes (act-3 reach 100% → 33%, "marginal"). Per content doctrine these are measurements — **nothing
retuned**, and nothing should be until the interactive playtest.

**Cost:** ~27% slower sim (`--enc` 1.18 s → 1.50 s). One Dijkstra per moving unit per decision tick,
cached per (target, range) per tick, and only on ticks a unit is free to step. Fine at 48 hexes;
poolable if it ever matters.

**Not eyes-verified in Unity.** The sim is fully verified headless and no event shape changed
(`MoveStart`/`Move` are identical), so `ReplayPlayer` needs nothing — but nobody has watched a fight
