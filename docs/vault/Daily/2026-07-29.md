## Revision presentation — time plays, and the split has a run-up (Jake)

- **Anchor selection plays time.** The walk to a new anchor was rebuilding the board every frame
  (`RenderRevisionFrame` → new FeedbackDirector, ResetDeaths, ClearFieldViews, ResetDress incl. a
  `Camera.main` reset), then fighting itself: ResetDress undid the held dress that the coroutine
  re-applied through a per-frame `FindFirstObjectByType<Volume>`. Split out
  `ReplayPlayer.ScrubRevisionFrame` — re-fold and re-place, nothing else — with one full teardown at
  the start of a walk. The ceremony's rewind sweep (~110 frames) rode the same expensive path and
  now uses it too. Rate raised: `scrubPerSecond` 0.16→0.30, `scrubMaxSeconds` 0.40→0.85.
- **The committed branch opens before the anchor.** `CommitRevision` re-simulates the whole battle
  from tick 0 under the same seed and opening, so every tick before `BranchTick` is frame-identical
  to what was already watched. The ceremony now rewinds past the anchor to `BranchTick − runUpSeconds`
  and plays *into* the split: new `RevisionPresentationPhase.RunUp`, a half-held dress
  (`runUpDress` 0.45) that releases into the existing landing punch, and the overlay's dial hidden
  with its copy fading out by mid-run-up so the board stays readable.
- `ReplayPlayer.PlayRevisionRunUp(stopBeforeTick)` halts the playhead one tick short of the branch,
  mirroring `_pauseBeforeTick` but without offering a final chance. Polling `CurrentTick` from the
  coroutine was rejected: a hitched frame would carry the playhead past the intervention and the
  branch event would land as loose combat noise instead of under the beat built to strike it.
- New tuning: `revision.runUpSeconds` (5), `revision.runUpDress` (0.45). `runUpSeconds = 0` restores
  the old cut-to-anchor landing; Reduced Motion takes that path unconditionally.
- Verified: 533/533 sim tests · headless client compile · Unity Editor compile clean (0 errors,
  0 warnings), new API present in the loaded assembly, `tuning.json` parses with neighbours intact.

## Revision time-selection UX pass (Jake: "the UX could use a polish pass")

The anchor choice was a blind dial: the rail drew Cast/Death landmarks, the anchors were a separate
wrapping row of buttons, and nothing connected them or said what a second was worth.

- **The rail is now the instrument.** One inset `revision-timeline__track` owns every positioned
  layer, so a marker, an anchor and the playhead at the same fraction land on the same pixel.
  Anchors are ticks ON the rail at `(maxSeconds − n) / maxSeconds`; a `NOW` label marks the right
  edge as the witnessed present.
- **Anchors are priced.** `Battle.ApplyBorrowedFuture` computes `carried = max(minimum,
  presentMana − manaAtBranch)`, and `manaAtBranch` moves with the anchor — so seconds are genuinely
  not interchangeable. Each anchor now shows its carry, and a readout line under the rail spells out
  `carry 33 → 25 Mana + 8 Shield`. Both moments were witnessed, so this reports a past fact and does
  not forecast the branch (ADR 0028 law 6). Wording is "returns before", never "undoes".
- **A playhead slides with the walk**, driven off `_revisionScrubClock` via a cheap
  `SetPlayhead(float)` that touches one style instead of rebuilding the anchors.
- **Markers carry their side and their subject.** Cast reads `Source`, Death reads `Target`; ally
  beats draw blue, enemy salmon. Marker tooltips were dead code — the elements set `tooltip` and
  `PickingMode.Ignore`, which cannot coexist — now pickable, and labels name the unit.
- **Reaching past a target now says so** instead of silently dropping the chip and reverting to the
  generic prompt: "Bram Oathkeeper cannot be reached at −4s."
- **The numbered steps were rendering backwards** — `.revision-combat__draft` is `flex-direction:
  row` and the column holding "2 · CHOOSE A MARKED TARGET" was added first, so it sat left of step 1.
  Order swapped; the divider moved to the control column with it.
- New `RunShell.EditorLoadRevisionDraftFixture(maxSeconds, withTarget, priced)` binds the draft with
  representative data so the rail is capturable without driving a run into a fight.
- Verified in Play Mode captures at 4 and 6 anchors (`client/McpCaptures/revrail-*.png`). Two real
  layout bugs were found only by looking: the anchor tick rendered at **zero height** (empty element
  + default `flex-shrink: 1` in a column, where height is the main axis), and the 50px anchor
  overflowed a 76px rail so the price row landed on the readout. Both fixed and re-captured.
- Still open: no keyboard/gamepad target cycling. ADR 0028's consequences ask for the overlay to work
  across mouse, keyboard, gamepad and touch; anchors have arrows and dpad, targets are board-click
  only. `EligibleRevisionTargetIds()` already exists to drive it.
