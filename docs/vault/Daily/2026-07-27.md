# 2026-07-27 — Audio: research, plan, and the gate that was missing

## What Jake asked

Audio is disabled because the UI stings were bad. Research how modern Unity games manage sound;
plan a UI system (**clicks only**, no hover, short and crisp) and a separate sim/replay system;
build tooling if needed, taking Shoota as the reference for *tooling*, not for clips.

## The answer to "why were they bad" is measurable, and it is not taste

Measured all 35 shipped clips. Three separable defects:

1. **5–20× too long.** 14 of 18 UI clips carry 0.5–1.0 s of *continuous audible content*
   (a click is 40–120 ms). `route_1` is a full second of sound for moving a resource.
2. **20 dB level spread.** `error_1` at −20.7 dBFS is the quietest thing in the set; `deal_2`,
   `seat_1`, `seat_2` sit at −0.0. The most important cue is the quietest.
3. **No shared identity.** Crest 13.7 → 32.9 dB across a set meant to be one instrument. Generated
   one prompt at a time with no family constraint.

Plus `commit_1` starting **157 ms** late — audible input lag.

**Root cause is process.** `hall-polish` records that all 18 clips "passed structural validation" —
that gate checked they *imported*. Nothing measured onset, length, level or crest. **So there was no
reason to expect a regenerated batch to be better than this one**, which is why the answer was
tooling before assets.

## Board audio was worse — undesigned rather than merely chaotic

`ReplayPlayer.PlaySfx` is one lazily-created `AudioSource` + `PlayOneShot(clip, 0.85f)`.
`PlayOneShot` layers, so it is unbounded overlap at a single priority; `AudioSource.priority` is
never set. Past 32 real voices **Unity culls by audibility**, so a `death` sting loses to four Burn
ticks. **No `AudioMixer` asset exists in the project at all** — item 9's volume sliders have nothing
to drive. 27 sound ids referenced, 17 clips exist: the whole per-weapon `hit_*` layer is authored
and mute.

## Research

Riot/TFT's Sandy Zhou gives the usable test — *"you must be able to state what stands out when
density rises, what steps back, and what the transition curve is"* — which §5.3 of the design page
now answers explicitly. Note the precedent that Riot's fix for unparseable 9v9 combat was a
**second, slower animation set**: the audio analogue is *don't sound every event*. Guildrun's
reviews praise "audio feedback on crits, heals, and relic procs" — three classes, all decisive.

Recommended **against** FMOD/Wwise (no 3D, no music, hard determinism contract — all cost) and
**against** Unity 6's `AudioRandomContainer` (an editor asset per family, fights JSON hot-reload).
Copy the middleware *vocabulary* instead. **Shoota's `SfxPlayer.cs` is already the right
architecture** and it is ours — port the subset, drop 3D/occlusion/`SfxRoles`.

## Three findings worth keeping

- **The worst-case fixture is `overtime`, not `castfest`.** `make sfx-density` measured every
  committed replay: castfest is the densest burst at 8.0 onsets/s over 16 s, but **overtime runs
  9.6/s for 3.6 minutes**. Peak density is survivable; sustained density is what exhausts a
  listener. THE WANING (item 11) is the fixture board audio must be judged against.
- **`lint` caught a real defect in `bake` on its first run.** Trimming the tail *before* filtering
  left up to 105 ms of sub-threshold tail, because the high-pass genuinely shortens a clip's audible
  span. Dead tail holds a pooled voice open for its whole length. The gate caught a bug in the tool
  that built the gate — which is the entire argument for having it.
- **The audition sheet had to be looked at, not just generated.** The obvious implementation
  normalises each waveform to its own peak, which makes a −11.9 dB source draw identically to its
  −5.0 dB bake and a 945 ms clip draw the same width as a 49 ms one — hiding the exact two things
  the page exists to compare. Fixed to absolute amplitude + a shared time axis per pair, capped at
  6× the baked length so a 50 ms tick is still inspectable. Verified in a real browser.

## Step 4 built too, once the lock freed

`UiAudioDirector` is now a ~90-line cue→family adapter over `SfxPlayer`. Hover, tooltip,
drag-projection and `Attention` silent · ten families → six · ambience bed, its duck, both

**A second law emerged while writing it:** the old `Family()` fell through to `"commit"` for
anything unmapped. Under clicks-only that is backwards — a default that makes noise means any
ambient signal added later starts clicking on its own. Now an unmapped *cue* is silent; an unmapped
*transaction* still commits, because a transaction is by definition something the player just did.

**The trap worth remembering.** `SfxPlayer` resolves `{id}_1..n` before bare `{id}`, and the shipped
set names every single-variant clip `_1`. Promoting the bake as `error.wav`/`major.wav` left the
**stale 1.04 s `error_1`/`major_1` shadowing them** — both files exist, both import, both play, no
warning anywhere. The two families would have loaded exactly the clips this pass exists to replace.
Caught by asking *which file would the loader actually pick*, not *did the copy succeed*. A fallback
chain plus a rename is a silent-wrong-answer machine.

**`make check-client` is new** (`tools/check-client-compile.py`): compiles all 57 client scripts
headless against real Unity reference assemblies borrowed from Shoota's Linux build. 0 errors. This
existed once and was lost; it is a make target now so it does not go again. Editor scripts are
excluded by construction — a player build ships no `UnityEditor.dll`.

## The mixer: `Unity_RunCommand` is currently unusable, so the asset self-creates

Lock finally freed, and then the *tool* was the blocker. `Unity_RunCommand` compiles into a library,
so top-level statements fail `CS8805` outright; a class-shaped payload compiles fine but the harness
then finds no entry point and returns *"Execution failed: No logs available"*. Five shapes tried,
including putting the class in the `Unity.AI.Assistant.Agent.Dynamic.Extension.Editor` namespace the
harness itself appends. `Unity_GetConsoleLogs` returns `totalCount: 0` for everything, which the
quirks memory (note 6b) already warns is not evidence of a clean console.

So "sync the script, call `ExecuteMenuItem`" — the documented pattern for exercising plugin code —
is not available to an agent right now. **Solution: make the asset self-create.**
`[InitializeOnLoadMethod] EnsureMixerOnLoad`, deferred through `delayCall` (the AssetDatabase is not
reliably ready during `InitializeOnLoadMethod` itself), guarded by the same existence check the menu
item uses. Unity builds the mixer on its next domain reload — no menu item, no MCP call, no lock.

**Deliberately did NOT hand-author the `.mixer` YAML**, even though Shoota's could have been adapted
and it would have unblocked verification immediately. An untestable hand-built mixer that resolves
no groups fails *identically* to having no mixer, except it leaves something in the repo that looks
right. Unity's own API keeps the built-in self-check (`FindMatchingGroups` across all five buses,
logged with a verdict) actually meaningful.

**A bug caught by reading the quirks memory rather than by testing:** editor scripts compile into
Assembly-CSharp-**Editor**, which cannot see `internal` types in Assembly-CSharp. My convenience
`Warband/Audio/Refresh SFX` menu item called `SfxPlayer.ClearCache()` — `SfxPlayer` is `internal`
like the rest of the presentation layer (`ReplayPlayer` is `public` only because it is a scene
MonoBehaviour). That would have been a hard compile error the moment Unity reloaded. Removed the
menu item rather than widening the type's access for a dev convenience. **`make check-client`
cannot catch this class of error by construction** — it excludes editor scripts, and says so.

**The reload happened and the mixer built itself.** Verified structurally rather than by presence:
five buses resolve, four params exposed, and `Decisive` serialises as a **sibling** of `Ducked` —
the single load-bearing detail, since a child would duck death and crit against themselves.

## A routing bug the report caught

Pricing the per-bus caps (`make sfx-density` now reports per-bus pressure) exposed that **the
per-weapon hit sounds are authored on `EventKind.Attack` — the swing — not `DamageDealt`**, which
carries no sound row at all. `BusFor` routed only `DamageDealt` to `Impact`, so **every weapon hit in
the game** was filed under `State`: lowest priority, smallest cap, first stolen. `Cast` bodies and
`CheatDeath` were mis-filed the same way. Fixed and re-priced — peak pressure Cast 1.7/4, State
1.6/3, Impact 1.0/6, Decisive 0.2/4, so no bus steals from itself on any committed fixture.

Found by measuring, not by reading the code. The report duplicates `BusFor`'s rule in Python, which
is a second source of truth — a handful of labelled offline-only lines. That trade bought a bug the
review did not.

## Item 1c — THE COMBAT RECAP (built; pixels unseen)

The client had **no graph of any kind**. It now has three, on the result gate: per-hero
contribution bars, the damage composition, and the death timeline.

**The fold went in the sim, not the client.** `Warband.Sim/CombatRecap.cs` turns a `FightSummary`
into the exact rows, segments and marker positions the panel draws; `CombatRecapPanel.cs` draws
them and computes nothing. The reason is that a chart fails in *arithmetic* — shares that don't
sum, a bar normalised to the wrong denominator, a zero-tick fight dividing by zero — and
arithmetic is testable headlessly while a Unity panel is not. 8 tests (`CombatRecapTests`), most
folding a hand-authored event log so each case states itself instead of hoping a simulated fight
happens to contain it.

**Two decisions that mattered more than the layout:**
- The bar is normalised to the **leader**, the number is the share of the **team**. Conflating
  those two denominators is *the* chart bug; six even contributors would each draw a 17% stub.
- Composition reads `UnitSummary.ByCause` rather than `FightStats`' five-way split, so **Counter
  and Trigger get their own slices for free**. Measured against the act-3 boss: CONTROL reads
  Attack 65 / Ability 19 / Counter 9 / Trigger 8 where DAMAGE reads Attack 92. The chart
  *discriminates builds* — which is the whole point of it existing.

**One correction to my own code, caught by writing the comment out loud.** I had the Waning marker
appear only when `EndTick > OvertimeStartTick`, and wrote a test comment claiming the storm "first
ticks the tick after the threshold". Checking `Battle.cs` instead of trusting it: the storm fires
at `_tick >= OvertimeStartTick`, so a fight ending exactly on tick 900 *has* taken storm damage.
Reporting no Waning there would have denied damage the log contains. Now `>=`.

**A fixture that would have lied.** The UI QA matrix already covers surface `result` — but its
fixture builds a synthetic `ResultGateModel`, which carries no recap, so the panel would have
hidden itself and the capture would have come back green over three charts that never rendered.
`CombatRecapPanel.EditorFixture()` now supplies deliberately the *worst* plausible case: a
four-digit heal on a zero-damage cleric, a name long enough to need its ellipsis, five composition
slices, clustered deaths, and the Waning on the track.

**Verified:** 485 tests (268 sim + 217 run) · `check-client` 0 errors · a second headless compile
with `DEVELOPMENT_BUILD` defined, because the standard check defines nothing and would have left
the editor-only fixture entirely unchecked · `make baseline` byte-identical, fingerprint
`3dba11673c26e858` — the recap changed no fight · numbers eyeballed on real act-3 boss fights
across all four probe axes.

**Not verified: a single pixel.** The gate exists only in Play Mode, and Codex was live in eight
client scripts while this was built, so taking the editor and forcing Play Mode was the wrong
trade. Height on phone is the live risk — the panel is contract-bound not to scroll.

## …and it shipped broken. What that cost, and what it taught

Jake played a fight and the recap was unreadable (`inbox/post-match-recaps/`). I called the pixels
unverified and shipped anyway; "unverified" was doing a lot of work in that sentence.

**The bug:** every element in UI Toolkit defaults to `flex-shrink: 1`. The result gate is capped at
`max-height: 94%` of a 900px reference viewport (1600x900, `match=1`). The recap pushed content past
that budget, and Yoga neither clipped nor scrolled — it **silently squashed every child**. 22px rows
resolved to ~11px, their 14px text spilled out of the box, and the *pre-existing* stat cards dropped
their values outside their own background. I had added ~276px to a panel with ~70px of slack and
never measured the budget.

**The process failure is the bigger one: a green layout contract is not evidence.** It reported PASS
over a broken screen twice.
- The contracts I added asserted **min-font** and **single-line width**. The break was vertical: the
  font never changed and nothing clipped horizontally, so they could not fail. `RequireMinimumHeight`
  already existed and is exactly the check — I did not use it.
- After fixing that, the **phone** layout drew composition, timeline and the recommendation on top of
  each other and *still* passed: overlapping siblings are each the right height and each inside the
  panel. Cause: `flex-basis: 0` + `flex-grow: 1` distributes the MAIN axis, which is width in the
  desktop row but **height** once phone flips it to a column — with no definite height to grow into,
  both columns resolved to zero.

Both were caught by opening the PNG. `UiLayoutContract` is a regression net, not a pair of eyes.

**Four more defects only the captures showed:** the board's own world-space end-of-fight banner drew
*through* the gate — two post-fight surfaces lit at once, now suppressed while the gate is up · the
QA fixture still printed the three death labels the shipping path had dropped, so it rendered a
screen the game no longer produces · the name label's `overflow: hidden` (needed for the ellipsis)
clipped its own descenders until given an explicit height · the exit buttons hung through the panel
border while `RequireInside` on their *row* passed, because the buttons overflow the row.

**Fixed and re-verified:** `flex-shrink: 0` on everything fixed-height · composition and timeline
side by side, since height is scarce and width abundant · the three death lines replaced by a
one-line `Lost:` caption · height assertions for every recap box, the columns, and the buttons.
New `Warband/UI QA/Run Result Gate Matrix` — five shots instead of the full matrix's 82, because a
run nobody will sit through is a run nobody does, which is precisely how this shipped.
**PASS at 1024x768/130%, 1280x720, 1600x900, 2556x1317 and phone, fixture at a six-hero worst case,
four of five captures read by eye.** 485 tests green, baseline byte-identical.

## Session 4 (late): the Banneret's Company — a roster, not a radius

**Jake's calls:** general layer, not banneret-only · rings stay up quietly for every placed
muster and brighten on selection. The second was the important one — you place the banner and
*then* place the allies, so a ring visible only while the banner is selected is dark during the
exact action it exists to inform.

**One definition of the rule, in content, not in the client.**
`MechanicalRulePresenter.Musters(UnitDef)` returns the unconditional BattleStart ally-radius rules;
`MusterSeats(def, hex)` turns that into the hexes to paint. Clipping uses the new
`RunController.IsDeployable`, extracted from `ValidatePlacement` — so the board and the validator
that refuses a lock-in are now literally the same predicate and cannot drift. The Unity client
pattern-matching triggers itself would have left a lying ring behind the first kit that retuned
(render-contract law #1). 13 headless tests.

Rendering reuses `FieldView` — the rim-then-floor ground sentence combat fields already speak —
with two additions: `ColorOverride` (own palette: `fields.muster`) and a rim/fill emphasis split.
Ring age is carried outside the view in `_musterAges`, because every deploy click re-snapshots and
rebuilds `_generated`; without it a standing ring replays its 0.2 s rim trace on every click.

**Capture-verified**, `Warband/MCP/Capture Muster Rings` (new editor harness — the UI-QA deploy
fixture is model-only and never touches the board, so it could not see a ring at all):
