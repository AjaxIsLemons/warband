## Session 2 (morning) — field flavor: zones colored by what they DO

Jake asked what was next and picked implementation on the render layer. Portal has no Unity MCP
(`--strict-mcp-config` in portal's `claude.go:268` restricts the surface to portal's own server), so
the work was chosen to be the part that is *fully verifiable headless* — which turned out to be the
actual blocker anyway.

- **The real reason fields all rendered yellow was in the sim, not the client.** `FieldCreated`
  carried `IsWall`, creator, attached-unit and radius — but nothing about what the glyph *does*. The
  client had no signal to color on, and `TellMatch` had no field filter to key on.

- **`FieldFlavor` (Neutral/Hazard/Boon/Buff/Debuff) — derived, not authored.** The tempting move was
  a new authored tag on `FieldDef`, but `Affects` already encodes the author's intent: a glyph aimed

  anywhere in the sim.** An all-affecting status pulse deliberately stays Neutral (grey) rather than
  guessing green or red. Flavor is orthogonal to `IsWall`: a burning wall is `wall+Hazard`.

  that honors the `-1` "unused" default as Neutral) → **replay v2** → `PlaybackField.Flavor` →

  needs.

- **Client half — EYES-VERIFIED.** `FieldTune` in `tuning.json` (hazard red · boon green · buff cyan ·

### Session 6 — Jake's live catch: frozen sharpshooters → firing-angle seek

Jake watched wallfort in the client and caught both sharpshooters standing motionless. Root
cause confirmed at Battle.cs:228: the greedy move step only accepts STRICTLY-closer hexes, and a
wall dead on the shot line is a local minimum — block-then-adapt turned the old infinite-whiff
version of this pre-existing hole into visible freezing. (The render layer was faithful; the sim
was the bug. Debugging law held: source of truth first.)

Fix (opus agent + review): when wall-blocked, the move step seeks a FIRING ANGLE instead of
proximity — unoccupied neighbor within weapon reach with a clear TraceProjectile line, min
distance, fixed direction order; plateau/backstep allowed only when it buys the shot (no
oscillation possible: clear line → next decision fires); fallback to the old greedy, else stand.
Non-blocked units byte-identical (proven again: 6/7 fixtures cmp-identical, only wallfort
changed). +3 tests → **203 green**. wallfort: 111→77 ticks, sidesteps at t0-1, sharpshooters
fight the whole match; captures show both archers strafed off the line, diagonal open, bows out.
Agent-idle-without-report happened again (2nd time) — direct tree verification first, ping for
the report after, worked fine as a pattern.

## Session 9 — replay v3: the snapshot finally says what a unit IS

Jake asked what we could build *around* a parallel session doing placement/bench UI, floating three
candidates: more class design, balance checking, or an art pipeline on the Unity AI credits. All
three got pushed back on, for reasons already written down:

- **More classes** — the first-playable content budget is a hard cap (ADR 0001 + 0016), 8 heroes.
- **Balance checking** — the content doctrine forbids a balance pass before the interactive
  playtest; the sweep already did the legitimate version (name outliers, tune nothing). Its own
  headline was that victory saturates ~99% at every tier, so the lever is the difficulty curve,
  which needs authored encounters that don't exist yet. Balancing now = balancing scaffolding.
- **Art pipeline** — real, but it's the *worst* concurrent choice: `Unity_AssetGeneration_*` is
  exactly the MCP surface the other session is using, and generated art has to slot into the
  Body-container/torso split the tells compose onto, so it wants an asset contract first.

**What we built instead was the thing blocking their work from below.** `PlaybackUnit` carried
Name/HP/Shield/Mana/Pos/Statuses and nothing else — no Range. `UnitDef.Range` has existed in the
sim the whole time and simply never crossed into the render contract, and `PlaybackUnit.From`'s own
comment binds placement previews to that one model. So a player deploying a Sharpshot could not be
shown that it reaches 4 hexes. No range overlay, no threat highlight, no "what is this" tooltip —
the decisions placement *is*.

- **Stat block** on the snapshot: Range · Attack · AttackInterval · MoveInterval · CritChance ·
  **HealAutos** (the censer law inverts what "attack" means — a support that "attacks" allies reads
  as a broken damage dealer without it).
- **Identity:** **ChassisId** · WeaponName · WeaponTier · **Traits** (spec nodes + trinkets in merge
  order, which is meaningful — last signature override wins). `Loadout.Compose` fills them; `Kits`
  stamps ChassisId from the dictionary key in one loop, so key and id can't drift.
- **Why ChassisId and not Name:** authored encounters rename freely ("Oathbound Bulwark") and the
  client keys silhouettes on the display name. Substring matching saves it *today* — a flavor-named
  enemy ("Ser Aldric") would silently fall through to the default shape.
- **Identity is hashed into `HashView`.** That was the judgment call: it costs time on every tick,
  but it is what gives the `make scenarios` round-trip (live hash == reloaded hash) teeth across all
  7 real fixtures instead of one synthetic test unit. A bug dropping WeaponName only at Relic tier
  would otherwise pass every fixture silently.
- **Replay v2 → v3.** Wrote the **first-ever unit test of the wire format** — it had only ever been
  exercised by the Viewer at `make scenarios` time. **203 → 217 tests.**

**Found in passing:** `client/Assets/StreamingAssets/replay.bytes` — which the scene's ReplayPlayer
still points at as its default `replayFile` — was stuck at **v1** and had been throwing
"Unsupported replay version" since the v2 bump. Pre-existing, not from this change, but it's the
same format I was versioning, so I regenerated it. Every `.bytes` in the tree is now v3.

**Honest cost:** the sweep went 4s → 5.3s. Hashing per-unit strings every tick is the price of the
round-trip coverage. Shaved 5.9 → 5.3 by sharing the Def-owned Traits list in `From` instead of
copying it per unit per tick — `_tickViewHashes` projects every unit every tick unconditionally, so
an allocation there multiplies by ~2,440 fights. Revisit only if the harness gets slow.

## Movement is a committed step, not a teleport (ADR 0018)

**Jake, watching a fight:** *"when I hit play on a fight, everyone teleports instantly. We need
smooth movement with solid sim rules for how it works."*

**The cause was structural, and worth stating plainly: this was never a rendering bug.** A move was
decided and applied in the *same tick*, so `MoveInterval` was a cooldown *between teleports* rather
than a travel time. The client did smooth it — `Lerp(..., 12f * dt)`, an ~80 ms time constant — but
a step is 500 ms, so the eye saw snap-then-wait-400ms-then-snap. Turning up the easing would only
have made the client draw units where the sim said they were not.

Render-contract §4 already flagged this exact lever: *"if wind-up or flight time ever affects
outcomes, it becomes a scheduled sim effect."* Travel time decides when a unit arrives. It is sim
truth. So the fix went in the sim, and the renderer got demoted to interpolating a window it is
handed. Law + rationale: **ADR 0018**.

**Cadence is unchanged** — depart T, arrive T+MI, free to depart again at T+MI is still one hex per
`MoveInterval`. The single real gameplay change is that everyone is one step *later* than before:
you can no longer be somewhere before you have walked there. And because arrival and the next
departure share a tick, a pursuit became one continuous slide instead of a hop every MI ticks —
that is the part that actually reads.

**Two rules carry most of the weight:**
- **The reservation.** A walker occupies BOTH hexes — the one it stands on and the one it is
  walking into. Hex-teleporting never had to think about this; without it, two bodies slide
  through each other.
- **A `Move` with no preceding `MoveStart` is a teleport.** That is the entire slide-vs-blink
  rule, and it is what keeps Leap spectacular for free.

**The guardrail earned its keep, twice.**
1. The walk is in `PlaybackUnit` and therefore in the view hash, so the per-tick reconstruction
   test now proves `MoveStart` is emitted *and* folded correctly — not just `Move`.
2. It was also the only test to fail, and for an honest reason: the kitchen-sink fixture's 60-tick
   Haste expired at t60, but its holder now dies at **t56**, so the fixture silently stopped
   covering `StatusExpired`. Shortened to 40 ticks with a note. Nothing was broken; the fight's
   timing moved by design and a fixture that was passing on a coincidence stopped.

**Verified in the Editor** (edit mode, `BuildPreview` per tick, positions measured against the
generated tiles as an external yardstick): mid-walk offsets `0.346 → 0.693 → 0.693 → 0.346 →
0.000` — linear across the sim's window, **exactly on the hex at the arrival tick**. Footfall
`0 → .0666 → .0411 → .0411 → .0666 → 0` (two steps per hex, flat at both ends), body yaw turning
330° → 30° onto each new path. Console clean. 272 tests green (was 263; +9 movement tests).

**Not verified, and say so:** the live per-frame loop. This Editor's player loop does not advance
while unfocused — `Time.frameCount` stayed at **1** across play mode with `isPaused=false` and
`timeScale=1`, and `QueuePlayerLoopUpdate` did not move it. The interpolation formula is the same
line in both paths and was exercised at five points along one step in edit mode, but the runtime
branches (`Smoothed = Walking ? Target : Lerp(...)`, the bob at framerate, tell anchoring during
play) have not been seen at 60 fps. One press of Play answers it.

**Feel knobs are hot-reloadable:** `tuning.json` → `motion` (`bobHeight`, `bobSteps`, `leanAmount`,
`turnSpeed`, `snapSpeed`). Position itself is deliberately NOT tunable — it belongs to the sim.
`snapSpeed` only ever applies to discontinuities (teleports, leaps, a rebuilt view); a walk is
taken exactly, never chased, or the body would trail its own truth again.

### The leap arc — the other half of the movement law

**Jake, immediately after:** *"I'm seeing the Shade teleport instantly, we need to build something
so it's a bit less jarring of a transformation."*

Fair, and it is the flip side of ADR 0018 rather than a miss: the law keeps a leap **instant in the
sim on purpose**, so the renderer had nothing to interpolate and fell back to its snap-lerp — across
half a board that is a smear that reads as a blink. There was also **no `Leap` tell authored at
all** in tuning.json, so it got nothing else either.

**The leap stays instant in the sim.** Modelling airtime would delay the Shade's arrival at the
backline, which is a *balance* change, and content doctrine says not before the playtest. So the
body gets an arc as decoration inside the tick — same class as a lunge or a tracer.

Three details did the work:
- **Both endpoints now ride the `Leap` event** (`Aux2`/`Aux3` = the hex it left). The fold has
  already teleported the unit by dispatch time, so the take-off is genuinely unrecoverable from view
  state — and inferring it from last frame's position would have silently produced a zero-length arc
  in frozen previews, which is exactly the kind of bug that only shows up in captures.
- **The offset is measured BACKWARD from the landing hex.** It decays to zero at the end regardless
  of frame timing, so touchdown is exact and the unit can never be parked off its hex.
- **An arc owns the body outright and vetoes lunges on that unit while it flies.** Both write
  `MotionOffset`; a swing landing inside the 0.44 s airtime would have fought it into a twitch.
  Found by reasoning about overlap, not by seeing it — `statusstorm` leaps mid-fight and would have
  hit it.

**Verified** (edit mode, `previewAdvanceSeconds` walked across the tell's life, positions measured
against tile transforms): crouch flat **on the take-off hex** → apex → **lands flat, exactly on the
landing hex**. `stomp` (6-unit leap) peaks at y=1.50; `statusstorm` (longer) at y=1.98 — height
scales with distance as designed. Console clean, 272 tests green.

Authored as a normal tell (`motion: "Arc"`), so airtime/height/colour/crouch are hot-reloadable
without a recompile. Violet, not fire-coloured: a displacement is not damage (palette law).
